          Architecture

          How a scan moves through AWS

          Two doors in, one queue, one worker, one job record. Writes and reads take different Lambdas, so a busy page never slows the PR gate.

          Pull request path Webhook intake + Scan worker

          1. GitHubsigned webhook
          2. API GatewayPOST /webhooks/github
          3. gk-webhookHMAC check, job
          4. SQSat least once
          5. gk-workercourse scanner
          6. DynamoDB + S3verdict, report
          7. Commit statussuccess / failure / error

          Paste path: write Paste and Scan · this page

          1. This pageserved by gk-results
          2. API GatewayPOST /scans, 1 per s
          3. gk-submitaccess code from SSM
          4. S3 + DynamoDBpasted/ · job QUEUED
          5. SQS5 tries, then DLQ
          6. gk-workercourse scanner

          Paste path: read Paste and Scan · this page

          1. This pagepolls 2 s, then 5 s
          2. API GatewayGET /scans/{id}
          3. gk-resultsread only, masks again
          4. DynamoDB + S3job item, report

          Why SQS in the middle

          gk-submit answers 202 in about a second. The slow scan runs in the background.

          • a failed try comes back after 360 s
          • 5 tries, then the dead-letter queue + an alarm
          • a burst waits in line, not at the door

          Why DynamoDB for status

          Every poll is one GetItem by job ID: small, fast, paid per request.

          • conditional writes: a retry never makes a 2nd job
          • TTL deletes old jobs (1 day pastes, 30 days PRs)
          • no joins needed, so no RDS bill all day

          Why polling, not WebSockets

          A scan takes seconds. Polling one small route is simpler and costs almost nothing.

          • every 2 s for 20 s, then every 5 s
          • stops at 2 minutes, then Check again
          • the job lives on the server, so a closed tab loses nothing

          Why INCOMPLETE is blocked

          Too big, a timeout, or nothing to scan means we never checked it. Not scanned is not safe.

          • PASS → success, merge allowed
          • FAIL → failure, merge blocked
          • INCOMPLETE → error, merge blocked

          Security built in

          • Only our routes5 for this page, 1 for GitHub. Any other path gets 404.
          • Rate limitsPOST /scans: 1 per second, burst 5. Polls have their own higher limit.
          • Access code in SSMSecureString. Never in git, the image or Terraform state.
          • Secrets maskedEach quoted secret keeps its first 4 characters. Same rule in worker and page.
          • Strict CSPOnly this page's own style and script run, checked by hash.
          • Private dataS3 blocks public access. gk-results holds no secret and its code never writes.

          Learner Lab: CloudFront is blocked, so gk-results serves this page over HTTPS. Roles cannot be made, so all 4 Lambdas run as LabRole. No VPC, so no NAT bill.
